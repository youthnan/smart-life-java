## 1. 简历项目条目（推荐版）

## 项目名称

黑马点评（hm-dianping）本地生活平台后端重构与智能助手扩展

## 项目描述（2-3 行）

基于 Spring Boot + MySQL + Redis 的本地生活平台后端，覆盖店铺、笔记、关注、优惠券与秒杀下单等核心业务；针对高并发场景优化缓存与异步链路，并接入 LangChain4j 智能助手能力，实现可观测、可演示、可扩展的一体化系统。

## 技术栈

Spring Boot、MyBatis-Plus、MySQL、Redis、Redisson、Redis Lua、Redis Stream、Kafka（可选缓存失效广播）、LangChain4j、DashScope(OpenAI兼容)、Nginx、Micrometer/Actuator。

## 个人职责（你可以直接放简历）

1. 设计并落地店铺多级缓存（Caffeine + Redis 逻辑过期 + Bloom 预判），解决缓存穿透/击穿问题。  
2. 实现秒杀下单高并发链路：Lua 原子校验 + Redis Stream 异步消费 + pending 补偿 + 用户维度幂等控制。  
3. 增加 Kafka 跨节点缓存失效广播（可选开关）及延迟双删机制，提升多实例一致性。  
4. 接入 Actuator + Micrometer 指标体系，新增缓存/Stream/Kafka 业务指标，支持故障定位与性能调优。  
5. 扩展智能助手能力（LangChain4j + Tool Calling + Redis 会话记忆），支持店铺查询与演示预约场景。  
6. 进行代码收敛与配置治理：统一缓存入口、剔除重复实现、敏感配置环境变量化。

## 结果与价值（建议按压测数据替换）

- 显著降低热点店铺查询对数据库的直接压力，提升系统高峰可用性。  
- 将秒杀写压力从同步落库转为异步削峰处理，提升整体稳定性与抗压能力。  
- 通过可观测指标体系实现问题快速定位，缩短排障时间。

## 4. 面试官追问与推荐回答

### Q1：你项目到底是 Kafka 还是 Redis Stream？

推荐答法：秒杀订单异步主链路是 Redis Stream；Kafka 在这个项目里用于多实例缓存失效广播，两者职责不同。

### Q2：为什么选择逻辑过期而不是强一致更新？

推荐答法：店铺详情属于读多写少，优先保障高并发可用性；逻辑过期允许短暂旧值，但能避免集中过期击穿 DB。强一致可以通过版本校验等方案叠加。

### Q3：如何保证 Stream 不丢消息？

推荐答法：ACK 在业务成功后执行，失败进入 pending-list 补偿，语义是至少一次；业务层有幂等校验做最终一致保障。

### Q4：你做了可观测具体指什么？

推荐答法：除了默认 JVM/HTTP 指标，我新增了缓存命中/重建、Kafka 发布消费、Stream 处理与补偿指标，可直接通过 Actuator 查询并接 Prometheus。
